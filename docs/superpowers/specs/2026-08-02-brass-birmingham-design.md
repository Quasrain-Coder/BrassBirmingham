# BrassBirmingham — 设计文档

v1.0，2026-08-02 定稿（brainstorming 阶段产出，经用户逐节确认）

> 本项目是桌游《Brass: Birmingham》规则的非官方、非商业数字实现（个人游玩），浏览器多人对局 + LLM AI 玩家 + 赛后复盘教练。允许使用原版美术与卡牌文字作为个人非商用素材（见 README Legal note）；无现成素材可用的部分自绘简化 SVG 兜底。

## 1. 目标与范围

- 完整规则：运河时代 + 铁路时代，2–4 人官方规则（含 2 人变体：部分 location 卡不入牌库、Warrington/Nottingham 商人位不铺商人板块——地点本身保留在版图上）
- 浏览器联机（局域网/公网自托管），权威服务器 + 房间短码
- AI 座位由 LLM（Claude API）驱动，行动空间受引擎硬约束
- 赛后生成完整复盘报告：关键决策点分析、具体替代方案及原因
- SQLite 持久化：对局、action log、复盘报告；支持断线重连与历史对局
- 非目标（YAGNI）：账号体系、聊天、移动端原生应用、MCTS（仅预留接口）、原版美术逐像素还原

## 2. 总体架构

TypeScript monorepo（npm workspaces，2026-08-02 由 pnpm 改为 npm：零安装、对本项目规模足够）：

```
packages/
  engine/    # 纯 TS、零依赖：完整规则 + 合法行动枚举 + 状态机，确定性、可单测
  server/    # Node + WebSocket 权威服务器，房间管理，SQLite (Drizzle) 落库
  web/       # React + Vite + SVG 棋盘客户端
  llm/       # LLM 玩家（虚拟座位）+ 复盘教练，调 Claude API
```

核心边界：**规则引擎是纯函数库**，被 server（权威裁决 + 合法行动枚举下发）、llm（行动空间枚举）、复盘（log 重放）复用同一份代码（web 不跑引擎，见 §7 修订）。

## 3. 规则引擎（engine）

### 状态（GameState，纯数据，可 JSON 序列化）

- `board`：静态图——20 个地点（Birmingham、Coventry、Dudley、Walsall 等）+ 板边 5 个商人位（Warrington、Shrewsbury、Nottingham、Gloucester、Oxford；按人数铺 3/4/5 块商人板块）、连接边（运河边 / 铁路边分开标注）；动态部分为地点产业槽位占用、已建连接。**卖货无需求轨**——只要求网络连接到显示对应图标的商人 + 消耗啤酒，不限量
- `players[]`：手牌、个人产业板块堆叠（每种产业按等级叠放，建造即弹栈）、现金、收入轨位置、收入等级、本回合已花费（决定顺位）、VP
- `resources`：煤需求轨、铁需求轨（价格随存量滑动）、啤酒（**逐块追踪**：啤酒桶放在未翻面酿酒厂上，运河时代 1 桶/铁路时代 2 桶，取走最后一桶时翻面；另有商人啤酒）。消耗商人啤酒触发该商人奖励（Gloucester develop / Oxford +2 收入 / Nottingham、Shrewsbury VP / Warrington £5）；一次卖货只能用所卖向那一位商人的啤酒。运输规则：**煤需要连通**（从煤市场买煤还需连接到商人），**铁不需要连通**（任意未翻面铁厂或铁市场直接取）
- `era`：`canal | rail`。时代切换清算：连接得分 + 翻面产业 VP、仅移除 1 级产业、移除运河连接、商人啤酒补满、重洗牌。铁路时代 network 行动可消耗 1 啤酒建第二条连接
- `turn`：当前玩家、本回合已执行行动数（1–2 动）、阶段标记
- `rng seed`：所有随机性走注入的种子随机数，保证 action log 重放逐字节一致。**牌库顺序为私有信息**（见 §4 视角过滤）

### 行动（Action，discriminated union）

`build / network / develop / sell / loan / scout / pass`，每个 action 携带完整参数（打哪张牌、建在哪个槽、卖货链路、啤酒来源等）。

两个核心函数：

```ts
enumerateActions(state, player): Action[]   // 合法行动全集——AI、前端提示、复盘共用
applyAction(state, action): GameState       // 纯函数；非法行动抛结构化错误
```

`applyAction` 收口全部子规则：build 连通性校验、煤的运输路径与消耗结算（铁无需连通）、sell 啤酒来源合法性、翻面触发收入轨前进等。

**行动枚举的规范化（canonicalization）**：资源来源选择（哪块煤、哪桶啤酒）默认按"最便宜/最短路"规则自动解析，不为等价来源枚举多个行动——只有来源选择产生实质差异（如触发不同商人奖励、耗干对手酿酒厂翻面）时才拆分为不同行动。否则 sell 链路 × 煤来源 × 啤酒来源的组合爆炸会拖垮 web 高亮和 LLM 预筛。**已定的简化**（M1 计划评审定稿）：sell 行动的多板块组合只枚举"每块单独卖"与"可卖全集"，中间子集不枚举（可用连续两次 sell 行动逼近）；overbuild 目标默认覆盖同地同产业最低级板块；scout 枚举全部 C(n,3) 弃牌组合（弃牌选择有策略意义，不规范化）。

### 规则数值配置化

产业数值表（成本/收益/翻面条件）、牌组构成、各人数起始设置放在 `engine/data/` 的 TS 常量文件，与规则逻辑分离，便于校对。

## 4. 服务器、房间与同步（server）

### 房间生命周期

`创建（人数、种子可选） → 大厅（等待加入） → 对局中 → 结束 → 存档`。房间号 6 位短码；无账号体系，昵称 + op token（localStorage），断线凭 token 重连回原座位。（M2 裁决：满员才能开始、任意座位成员可开始；AI 座位属 M3；token 经私密 `credentials` 消息单发，广播的 room_state 不含 token）

### 同步协议（WebSocket，JSON）

权威服务器模型，客户端永不本地推进状态：

- 下行：`state_snapshot`（按座位视角过滤后的全量快照 + 递增 seq；Brass 状态小，全量优于增量 diff）、`action_applied`、`error`
- 上行：`submit_action`、`ping`
- **视角过滤**：私有信息按座位过滤——只发自己的手牌，其他人只有牌数；**牌库顺序同样隐藏**（下发牌数而非序列），否则客户端可推算后续摸牌。服务器内存中保留完整状态用于重放
- 断线重连：重连后拉最新快照，seq 对齐
- 真人回合无强制超时，v1 仅"提醒"按钮

### 持久化（SQLite via Drizzle）

- `games`：id、房间配置、初始种子、最终状态、时间戳
- `actions`：game_id、seq、player、action JSON（对局 = 初始状态 + action log，重放/断线重连/复盘共用此数据）
- `seats`：game_id、seat、nickname、token（UNIQUE）——断线重连凭据（2026-08-03 随 M2 计划新增）
- `reviews`：game_id、player、报告 markdown、模型、token 用量（M4 落地）
- **声明：服务器重启即丢进行中的对局（内存房间/会话不恢复）；重放恢复属 M5**

### 错误处理

引擎非法行动错误带结构化 reason，透传前端显示；LLM 座位连续非法行动时降级（见 §5），对局永不卡死。

## 5. LLM 玩家（llm）

原则：**LLM 只做"选择"，不做"计算"**；规则结算永远在引擎，行动空间被 `enumerateActions` 硬约束。

决策流程（轮到 AI 座位）：

1. 引擎枚举合法行动全集；**启发式预筛**（板块等级、连通性、资源可得性、收入轨收益）剪到 Top ~20 候选
2. 组装 prompt：结构化文字局势摘要（非 JSON dump：资金/收入/手牌、各人产业与网络、市场价格与存量、时代与轮次）+ 候选行动列表（每个附一句话解释）
3. Claude API（Sonnet 级），tool use / structured output 强制返回候选编号 + 一句理由；理由显示在游戏日志中
4. 引擎校验合法性；非法 → 带原因重试一次 → 再非法降级为预筛 Top 1 并日志标注

难度分层：简单（Top 8 + 高速模型）/ 普通（Top 20）/ 困难（Top 40 + 两轮前瞻摘要）。

成本与延迟：prompt 前缀模板化吃缓存；单次决策目标 < 10s / < $0.01。服务器 key 走环境变量，`.env` gitignored，提供 `.env.example`。

接口预留：`PlayerAgent` 接口（`chooseAction(state, legalMoves) → Action`），实现含 LLMAgent、RandomAgent（测试）、未来的 MCTSAgent。

## 6. 复盘教练（llm + engine）

输入为落库的 action log；输出为按玩家生成的 markdown 报告（只分析本人操作）。

生成流程（赛后点击触发，异步，完成推送）：

1. **重放标注（确定性）**：重放 log，在每个决策点重新 `enumerateActions`，用启发式评估函数给实际选择与候选 Top N 打分；产出每步分差、分差最大 Top 10 决策点、时代切换站位统计
2. **LLM 分析（Opus 级）**：Top 决策点分批送入，每点附局面摘要、实际选择、候选替代、启发式分差；要求：
   - 判断启发式分差是否"真错误"（识别启发式看不出的长线布局并辩护）
   - 给出具体替代操作与原因链（引用具体回合与板块，禁止空泛建议）
3. **报告结构**：总评（打法风格识别）→ 3–5 个关键转折点逐手分析 → 时代切换站位评估 → 下局 1–3 条可执行建议 → 每手启发式分差曲线图

设计要点：启发式先行找"最值得讲的 10 手"，LLM token 花在刀刃上；分差曲线是客观锚点。报告按需生成（不自动烧 token），每局每人一份，用量入 `reviews` 表。

**2026-08-11 M4 计划裁决**：
- **报告完全公开**：拿到 game_id 即可为任意座位生成/查看报告，无权限概念（局域网自托管定位）
- **缓存优先 + 显式重新生成**：`reviews` 表已有该座位报告则直接返回；页面提供"重新生成"按钮显式覆盖，避免误点烧 token
- **模型与成本**：Opus 级 + 单次报告 token 上限（50k input / 8k output），超限先砍低分差决策点（10→5）再截断；LLM 分析不可用时降级为纯标注数据模板报告并明确标注
- **M4 不做逐步回放器**：报告页 = markdown + 分差曲线（点击曲线点显示该手文字局面摘要）；跳回合只读棋盘回放推迟到 M5

## 7. 前端（web）

- 官方素材版图（2026-08-19 修订，原为"自绘简化 SVG 地图"）：底图 = 官方版图扫描（ikegami/tts_brass 的 Steam UGC 源，个人非商用；`npm run fetch-assets -w @brass/web` 下载加工到 `packages/web/public/assets/`，素材不进 git），动态层叠加：已建产业 = 官方板块图（产业-等级-玩家色，翻面用背面）、已建连接 = 沿印刷路径玩家色折线、商人板块/啤酒/市场方块/VP收入标记叠于印刷轨道、可选目标黄铜发光高亮；坐标为人工标定的 6144 像素系（`web/src/board/geometry.ts`）；城市名叠加中文铭牌
- 交互围绕 `enumerateActions`：**合法行动由服务器随快照下发**（`legalActions` 字段，2026-08-03 由"浏览器本地预检"修订——server 本就要权威校验，枚举成本可忽略，免去 web 端引擎版本同步）；可打的牌高亮、可建槽位亮边，点击构造 action 提交——非法操作在 UI 层不可能出现，服务器校验兜底
- 面板：手牌（官方卡面图 + 中文牌名）、玩家板块（现金/收入等级/VP + 官方板块缩略图）、行动日志（含 AI 理由）、回合顺位条；煤/铁市场与收入轨/VP 直接渲染在版图上（无独立侧边栏）；UI 文案全中文（`web/src/game/display.ts` 统一文案层）
- 复盘报告页：markdown 渲染 + 分差曲线（点击曲线点显示该手文字局面摘要；跳回合只读棋盘回放推迟到 M5，2026-08-11 修订）

## 8. 测试策略

- 引擎（密度最高）：规则数据表驱动单测；种子固定重放一致性测试；**RandomAgent 随机对局 fuzz**（数千局，断言无非预期异常、必然终止、分数可解释）
- 服务器：协议层集成测试（建房/加入/行动/断线重连）
- LLM：client 接口可注入，测试用录制 fixture，CI 不烧 token
- CI（GitHub Actions）：lint + typecheck + 全部测试；**新增模块必须同步更新 CI test/coverage 步骤**

## 9. 里程碑

1. **M1 引擎**：完整规则 + enumerateActions + RandomAgent fuzz 通过（最大工作块，纯后端）
2. **M2 可玩**：服务器 + 房间 + 最小可用前端，真人浏览器对局
3. **M3 AI 入局**：LLM 座位 + 降级链 + 难度档
4. **M4 复盘**：评分标注器 + 报告生成 + 报告页（分差曲线）
5. **M5 打磨**：断线重连完善、历史对局列表、跳回合只读回放器、Docker 一键部署、README 完整化

每个里程碑结束均为可运行、可演示状态。

## 10. Git 工作流（沿用 Fortuna 约定）

- 禁止直接向 `main` 提交/推送，无任何例外；改动必须 分支 → push → PR → 合并
- 分支命名：`feat/...`、`fix/...`、`docs/...`、`refactor/...`
- PR 合并前 CI 必须通过；设计层面变更同步更新本文档
- Claude 参与的提交带 `Co-Authored-By` 尾注
